# OB15 arms-only control (`ob15_arms`)

OB15 has two robot types. They share the same low-level code (`OB15Arms` subclasses `OB15`); the arms-only
type just leaves the base, head and lift out of what a policy or teleop can command.

| | `ob15` | `ob15_arms` |
|---|---|---|
| Use for | VR setup, navigation, recovery | Recording tasks and running policies |
| Actions | 18: arms, grippers, head, base velocity, lift | 12: arms and grippers |
| Head and lift | Commanded by teleop/policy | Moved to a hold pose at connect, then re-commanded every tick |
| Base | Commanded | No base command is sent, so the wheels stay at zero velocity |
| Hold-pose code (`hold_from`, `station`, `rest_pose`, `ob15_hold.json`) | No | Yes (`robots/ob15_arms/`) |

In the usual setup both run on the robot computer (the Jetson) and the policy runs through remote inference, so
ZMQ is not involved. The ZMQ types (`ob15_client`, `ob15_arms_client`) still exist for a PC-side client talking
to an `ob15` host, and use the same hold options.

- **Action space:** 12 values (both arms and grippers).
- **Observation state:** arms, grippers, head pan/tilt and lift height. No base velocity.
- Base, head and lift keys sent by VR teleop or a policy are dropped.
- Recording runs on the Jetson. Inference runs on the Jetson with the policy on a GPU PC through
  [remote inference](./remote_inference) (`lerobot-policy-server` + `--inference.type=remote`).

## Station file

Stations live in `~/.ob15/stations.json` (override with `--robot.stations_file`):

```json
{"kitchen_counter": {"head_pan.pos": 0.0, "head_tilt.pos": -35.0, "gantry.height_mm": 220}}
```

Create one from Python:

```python
from lerobot.robots.ob15_arms.stations import save_station

save_station("~/.ob15/stations.json", "kitchen_counter",
             {"head_pan.pos": 0.0, "head_tilt.pos": -35.0, "gantry.height_mm": 220.0})
```

Hold target precedence: explicit `--robot.head_pan / head_tilt / lift_height_mm` > `--robot.hold_from` >
`--robot.station` > the current pose at connect. A key missing from a higher source falls back to the next one
(the log line "Hold targets ..." shows which sources were used). `--robot.hold_on_connect=false` freezes the
current pose and ignores `hold_from` and `station`.

## The dataset remembers the hold pose (`hold_from`)

- **Recording** with `ob15_arms` writes the resolved head/lift pose to
  `<dataset_root>/meta/ob15_hold.json` (also on resume). It is uploaded with `push_to_hub`. If the file already
  exists with a different pose (beyond the tolerances) it is kept and a warning is logged; pass
  `--dataset.overwrite_hold=true` to replace it.
- **Training** (`lerobot-train`) copies it to `<checkpoint>/pretrained_model/ob15_hold.json` when the training
  dataset has one (nothing happens for other datasets). A merged dataset only carries it if you copy
  `meta/ob15_hold.json` into it.
- **Inference**: `--robot.hold_from=<dataset or policy>` moves the head/lift to the saved pose. It accepts a
  local dataset root, a checkpoint directory (or its `pretrained_model/`), the JSON file itself, a Hub dataset
  id or a Hub model id. A local path that does not exist is tried as a Hub repo id.

```json
{"version": 1, "robot_type": "ob15_arms",
 "hold": {"gantry.height_mm": 220.0, "head_pan.pos": 0.0, "head_tilt.pos": -35.0},
 "source": {"station": null, "hold_from": null,
            "overrides": {"head_pan": null, "head_tilt": -35.0, "lift_height_mm": 220.0},
            "hold_on_connect": true},
 "recorded_at": "2026-11-09T12:00:00+00:00"}
```

## Rest pose and tolerances

- `--robot.rest_pose='{"left_arm_shoulder_lift.pos": -90, ...}'` (arm/gripper keys only, otherwise `ValueError`):
  sent first with head and lift frozen where they are, then after about 2 s the head/lift move to the hold pose
  while the rest pose keeps being sent. Use it to fold the arms clear of the body before the lift moves.
- `--robot.settle_timeout_s` (default 15), `--robot.lift_tol_mm` (5) and `--robot.head_tol` (2 deg) decide when
  the hold pose counts as reached at connect and when `check_hold()` reports drift.

## Commands

```bash
# Record on the Jetson (VR teleop still works; base/head/lift inputs are ignored)
lerobot-record --robot.type=ob15_arms --robot.station=kitchen_counter ...

# Run a policy served from the PC (on the PC: lerobot-policy-server --config_path=server.yaml)
lerobot-rollout --robot.type=ob15_arms --robot.station=kitchen_counter \
  --inference.type=remote --inference.endpoint=tcp/<pc-ip>:7447 --inference.deployment=<name> ...

# Restore the head/lift pose the policy's data was recorded with (dataset id, policy id or local path)
lerobot-rollout --robot.type=ob15_arms --robot.hold_from=<user>/<dataset> \
  --inference.type=remote --inference.endpoint=tcp/<pc-ip>:7447 --inference.deployment=<name> ...
```

## Checking head and lift

- `robot.check_hold()` returns, per hold key, the target, the actual value, the error and whether it is within
  tolerance (2 deg for the head, 5 mm for the lift), and logs a warning for any drift. It also runs when the
  robot disconnects. Call it at the end of a task or episode to confirm the head and lift stayed put.
- For recorded data, `python -m lerobot.robots.ob15_arms.scripts.convert_to_arms_only --src-repo-id <repo> --report`
  lists, per episode, the start and end values and range of head pan/tilt and lift, plus any base motion.

## Converting an existing full-body dataset

```bash
python -m lerobot.robots.ob15_arms.scripts.convert_to_arms_only --src-repo-id me/ob15_full --dst-repo-id me/ob15_arms
```

This writes a new dataset (the source is untouched) whose `action` has the 12 arm keys and whose
`observation.state` has no base velocity, and recomputes the stats. Check the `--report` output first and consider
dropping episodes where the head or lift moved a lot.
